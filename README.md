# DabbaTiffin

A digital canteen app: subscribe or pre-book breakfast and lunch a day ahead, pick from a
rotating veg menu, see the full price upfront, and skip meals until midnight. Batched
delivery to PGs, hostels, campuses and offices around Pune.

Implements the DabbaTiffin mockups (`DabbaTiffin Mockups.dc.html`) as a real app:

- **Frontend**: React + Vite + Tailwind CSS
- **Backend**: FastAPI + SQLAlchemy
- **Database**: PostgreSQL (SQLite locally if `DATABASE_URL` is unset)
- **Auth**: email/password with JWT bearer tokens
- **Payments**: simulated (no real payment gateway) — bookings and subscriptions are marked
  paid instantly, deducting from the in-app Tiffin wallet when that's the chosen method

## Demo login

The backend seeds a ready-to-use account on first boot:

```
email:    demo@dabbatiffin.in
password: Dabba@123
```

It comes with an active breakfast subscription, order history, a ₹210 wallet balance, and a
delivery point already set, so you can log in and place an order immediately. The login
screen also has a "Use it" shortcut that fills these in.

## Local development

Backend:

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Without a `DATABASE_URL` set, it uses a local SQLite file and seeds demo data automatically
on startup — nothing else to configure for local dev.

Frontend:

```bash
cd frontend
npm install
echo "VITE_API_URL=http://localhost:8000" > .env.local
npm run dev
```

Open http://localhost:5173.

## Dish photos

`frontend/public/dishes/*.jpg` ships with generated placeholder images so the app always has
something to render. To replace them with real, freely-licensed photos from Wikimedia
Commons:

```bash
pip install -r scripts/requirements.txt
python scripts/fetch_dish_images.py
```

It searches Commons per dish and falls back to the placeholder if a lookup fails, so it's
always safe to re-run. Commit the resulting files.

## Deploying to Render.com

This repo includes a `render.yaml` Blueprint that provisions three resources:

1. **dabbatiffin-db** — a managed Postgres database
2. **dabbatiffin-api** — the FastAPI backend (Python web service)
3. **dabbatiffin** — the React frontend (static site)

To deploy: push this repo to GitHub, then in Render choose **New → Blueprint** and point it
at the repo. Render will read `render.yaml` and create all three services.

### Environment variables

Render wires most of these up automatically from `render.yaml`; the ones marked "you set
this" need a value from you (either in the Render dashboard or by editing `render.yaml`
before deploying):

| Service | Variable | Notes |
|---|---|---|
| dabbatiffin-api | `DATABASE_URL` | Auto-filled from the `dabbatiffin-db` database |
| dabbatiffin-api | `JWT_SECRET` | Auto-generated by Render |
| dabbatiffin-api | `JWT_EXPIRES_MINUTES` | Defaults to `43200` (30 days) |
| dabbatiffin-api | `CORS_ORIGINS` | **You set this** — your frontend's Render URL, e.g. `https://dabbatiffin.onrender.com` |
| dabbatiffin (frontend) | `VITE_API_URL` | **You set this** — your backend's Render URL, e.g. `https://dabbatiffin-api.onrender.com` |

Render assigns service URLs containing your account/region-specific subdomain, so after the
first deploy, check the actual URLs Render gave each service and update `CORS_ORIGINS` and
`VITE_API_URL` to match (then redeploy) if they differ from the placeholders in
`render.yaml`.

Demo data (delivery points, dishes, rotating menu, and the demo account) seeds automatically
the first time the API boots against the Postgres database — no manual migration step needed
for this MVP.

## What's simulated / out of scope for this MVP

- **Payments** are simulated — there's no real UPI/payment gateway integration.
- **Delivery point locations** are static Indian addresses (Kothrud, Hinjewadi, etc. in
  Pune) for realism; there's no live GPS or maps.
- **No admin/kitchen dashboard** — menus, delivery batches, and order statuses are seeded
  directly in `backend/app/seed.py` rather than managed through an admin UI.
